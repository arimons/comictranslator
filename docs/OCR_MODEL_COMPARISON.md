# Step 4 OCR/번역 모델 비교

측정일: 2026-08-14
정본: no (의사결정 기록)
목적: `--ocr-model` 기본값을 수치로 결정하기 위한 비교.

---

현재 기본값(2026-10-20)은 OpenAI 전환으로 `gpt-6.1-sol`이다. 아래 수치는 기존 모델의 과거 비교 기록이며 GPT-6.1 Sol·GPT-6 Luna의 품질 측정 결과가 아니다. 새 기본값은 모델 접근·이미지 JSON 응답 계약만 실제 확인했으며 페이지별 번역 품질은 별도 확인한다.

## 실험 설계

Step 1~3(Cloud Vision → Text Grouping → 대사 추출)은 모델과 무관하므로 한 번만 실행하고,
**동일한 indexed OCR sheet**를 세 모델에 넣어 Step 4만 교체했다.

- 이미지 5장: `00003`, `00007`, `00031`, `00032`, `00035`
- region 합계 29개 (6 / 3 / 8 / 11 / 1)
- 프롬프트는 `text_scale_class` 제거 후 버전 (커밋 `f05eaa6`)
- 실행 15회 전부 정상 종료 (rc=0)

```bash
python3 -m pipeline.gemini_ocr_translate_v5 <image> <text_groups> <out> \
    --ocr-sheet-image <sheet> --ocr-sheet-json <regions> --model <MODEL>
```

## 구조 지표

| 모델 | 기대 region | 반환 cluster | 누락 | 빈 번역 | OCR 중복 | 재시도 | 총 시간 |
|---|---|---|---|---|---|---|---|
| `gemini-3-flash-preview` | 29 | 28 | 1 | 0 | 0 | 0 | **37.2s** |
| `gpt-5.6-luna` | 29 | 29 | 1 | 0 | 0 | 0 | 60.3s |
| `gpt-5.6-terra` | 29 | 28 | 1 | 0 | 0 | 0 | 65.4s |

**구조 지표는 세 모델이 동일하다.** region_id 오할당(OCR 중복)이나 빈 번역, 재시도가
한 건도 발생하지 않았다.

누락 1건은 세 모델 모두 `00007`의 같은 region(unboxed_rect `[732, 1395, 68, 72]`, 68×72px)이다.
모델이 일제히 건너뛴 작은 영역이므로 모델 품질 문제가 아니라 Step 3이 노이즈를
region으로 올린 쪽에 가깝다.

## 출력 품질 지표

구조가 같으므로 실제 출력 문자열을 비교했다. 여기서 갈렸다.

| 모델 | 번역문 수 | `・・・` | 전각 `？!` | `…` | 일본어 잔존 |
|---|---|---|---|---|---|
| `gemini-3-flash-preview` | 28 | **0** | **0** | 10 | 0 |
| `gpt-5.6-luna` | 29 | **4** | **5** | 3 | 0 |
| `gpt-5.6-terra` | 28 | **0** | **0** | 9 | 0 |

`・・・`(가타카나 중점 3개)와 전각 `？`, `！`는 **한국어 번역문에 남으면 안 되는 문자**다.
luna는 원문의 말줄임표를 `・・・`로 읽고 그대로 번역문에 옮긴다.

```
원문 なんだ…？
  gemini  뭐지…?
  terra   뭐야……?
  luna    뭐야・・・？      ← 중점과 전각 물음표가 번역문에 그대로 남음
```

## 번역 정확도

OCR 원문이 3모델 완전 일치한 것은 30건 중 11건이고, 나머지 19건은 말줄임표 표기
차이가 대부분이다. 다만 의미가 갈리는 사례가 luna에 몰려 있다.

| 원문 | gemini | terra | luna |
|---|---|---|---|
| `下がれ!!` | 물러나!! | 물러서!! | **내려가!!** |
| `…は？` | …뭐? | …응? | **…는?** |
| `それにしても` / `それにしては` | 그렇다 해도 | 그것치고는 | 그렇다기엔 |

`下がれ`는 "물러서라"는 명령인데 luna는 "내려가"로 옮겼다.
`は？`는 반문 감탄사인데 luna는 주격 조사로 보고 "는?"으로 옮겼다.
둘 다 문맥을 놓친 오역이다.

`それにしても` vs `それにしては`는 gemini 1 대 GPT 2로 갈렸다. 이건 OCR 판독 차이라
어느 쪽이 맞는지는 원본 확인이 필요하다.

## 결론

**기본값은 `gemini-3-flash-preview`를 유지한다.**

- 구조 지표 동률
- 문장부호 처리 깨끗함
- 번역 정확도에서 오역 없음
- **가장 빠름** (terra 대비 1.8배)

`gpt-5.6-terra`는 품질상 동등한 대안이다. Gemini 쪽 장애나 할당량 문제가 있을 때
바로 교체할 수 있다. 다만 1.8배 느리다.

`gpt-5.6-luna`는 **권장하지 않는다.** 저렴하지만 번역문에 일본어 문장부호가 남고
문맥 오역이 나온다. 이 파이프라인은 "텍스트 인식과 번역만 잘되면 되는" 것이 목표라
바로 그 지점에서 약하다.

### 남은 관찰

- 표본이 5장 29 region이라 구조 지표가 셋 다 완벽한 것은 이 표본이 쉬웠을
  가능성이 있다. 어려운 페이지(`00107` region_id 오할당 케이스 등)를 포함하면
  갈릴 수 있다.
- `render_hint`를 프롬프트에서 빼면 지시가 11줄 더 줄어든다. luna를 다시 볼
  일이 있으면 그때 재측정할 값이 있다.
- 속도 차이는 `OPENAI_REASONING_EFFORT`(현재 `low`) 조정으로 좁힐 여지가 있다.
